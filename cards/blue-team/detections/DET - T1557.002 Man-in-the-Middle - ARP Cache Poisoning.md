### Summary
---
**What it is:** Detecting ARP spoofing attacks where attackers send forged ARP replies to associate their MAC address with legitimate IP addresses (typically the default gateway) to intercept, modify, or redirect network traffic on local networks.

**Scope:** This note covers detecting ARP cache poisoning through analysis of gratuitous ARP replies, duplicate MAC-to-IP mappings, unsolicited ARP responses, abnormal ARP traffic patterns, and gateway redirection indicators using network monitoring and packet analysis.

**Prerequisites:**

- [[Address Resolution Protocol (ARP)]]
- [[Man-in-the-Middle Attacks]]
- [[Network Packet Analysis]]

**Required Log Sources:**

- Network packet captures (PCAP)
- Network traffic logs from switches or taps
- ARP cache logs from endpoints
- SIEM ingesting network traffic data

## How It Works (2-4 lines)
---

Address Resolution Protocol (ARP) maps IP addresses to MAC addresses in local networks, with devices broadcasting `who has` requests and receiving `is-at` replies to build ARP caches for communication. Network administrators rely on ARP for legitimate local network address resolution and connectivity. ARP spoofing exploits the protocol's lack of authentication by sending unsolicited forged ARP replies claiming ownership of IP addresses (typically the default gateway), causing victims to update their ARP cache with the attacker's MAC address and route traffic through the attacker's system. Defenders detect this by identifying gratuitous ARP replies, duplicate MAC-to-IP mappings where multiple MAC addresses claim the same IP, unusual ARP traffic volume, and mismatches between legitimate network infrastructure MAC addresses and those in ARP responses.

## ARP Spoofing Concept
---

**Address Resolution Protocol (ARP):** Maps IP addresses to MAC addresses in a local network.

**Attack Mechanism:**

Attacker sends fake ARP replies (`is-at` messages) to trick devices into associating the attacker's MAC address with a legitimate IP, most often the IP of the default gateway. This allows the attacker to intercept, modify, or redirect traffic.

**Why This Works:**

- No authentication needed
- No ARP request was made
- The attacker is not even asked
- Victims will accept the response and update their ARP cache

**Why Default Gateway is Also Spoofed:**

If you only poison the victim:

**Victim thinks:**
```C
Gateway IP -> Attacker MAC
```
So victim sends internet traffic to attacker.

**But the gateway still thinks:**
```C
Victim IP -> Victim MAC
```
So replies go directly back to the victim.

**Solution:** Attacker must poison BOTH victim and gateway for bidirectional interception.

## Detection Workflow
---

**Legend:**

- `{GATEWAY_IP}` = 192.168.10.1 (default gateway)
- `{VICTIM_IP}` = 192.168.10.16
- `{ATTACKER_MAC}` = 02:fe:fe:fe:55:55
- `{LEGITIMATE_MAC}` = 02:aa:bb:88:b1:96
- `{DOMAIN}` = corp-login.acme-corp.local

**Context:** Network monitoring has captured ARP traffic. You need to identify potential ARP spoofing attacks targeting local network devices.

---

### 1. Baseline ARP Traffic Patterns

**Detection Method:**

- Capture and analyze normal ARP traffic during baseline period
- Filter for all ARP packets:
```C
arp
```

**Note:** Press CTRL + ALT + 1 in Wireshark to fix time display format.

**Observable Patterns:**

**Normal ARP Request (`who-has` - Opcode 1):**
```C
Address Resolution Protocol (request)
Opcode: request (1)
Sender MAC address: 02:aa:bb:88:b1:96
Sender IP address: 192.168.10.16
Target MAC address: 00:00:00:00:00:00
Target IP address: 192.168.10.55
```

**Explanation:**
1. Physical address of device asking the question
2. IP address of requesting device
3. In ARP request, sender does NOT know target's MAC address yet, so fills with all zeros
4. This is the IP address the sender is trying to find

**Normal ARP Reply (`is-at` - Opcode 2):**
```C
Address Resolution Protocol (reply)
Opcode: reply (2)
Sender MAC address: 02:fe:fe:fe:55:55
Sender IP address: 192.168.10.55
Target MAC address: 02:aa:bb:88:b1:96
Target IP address: 192.168.10.16
```

**Explanation:**
1. Device responding to the `who-has` question
2. Confirms what IP it owns
3. MAC of device that originally asked
4. IP of device that asked the question

**Baseline Characteristics:**
- ARP requests followed by corresponding replies
- Consistent MAC-to-IP mappings
- Low ARP traffic volume (periodic requests)
- Gateway MAC address matches known network infrastructure

---

### 2. Detect Gratuitous ARP Replies

**Detection Method:**

- Filter for gratuitous ARP replies (unsolicited):
```C
arp.isgratuitous
```

**Malicious Gratuitous ARP Example:**
```C
[Is gratuitous: True]
Sender MAC address: 02:fe:fe:fe:55:55
Sender IP address: 192.168.10.55
Target MAC address: Broadcast (ff:ff:ff:ff:ff:ff)
Target IP address: 192.168.10.55
```

**Indicators:**

1. **No one asked:** No corresponding ARP request for this reply
2. **MAC address claim:** "This MAC address belongs to the IP I'm about to mention"
3. **IP ownership:** The IP the sender claims ownership of
4. **Broadcast to everyone:** `ff:ff:ff:ff:ff:ff` sends to all devices on local network
5. **Target IP and Sender IP are the same:** "For anyone keeping track - 192.168.10.55 is me (02:fe:fe:fe:55:55)"

**Why Suspicious:**

Legitimate gratuitous ARP used for:
- Announcing new network presence
- Detecting IP conflicts
- Updating ARP caches after network changes

**Malicious indicators:**
- Repeated gratuitous ARP for gateway IP
- High frequency (multiple per second)
- From MAC addresses not matching known infrastructure

---

### 3. Identify Duplicate MAC-to-IP Mappings

**Detection Method:**

- Filter for duplicate IP address mappings:
```C
arp.duplicate-address-detected || arp.duplicate-address-frame
```

- Or manually identify by filtering ARP replies for same IP:
```C
arp.opcode == 2 && _ws.col.info contains "192.168.10.1 is at"
```

**Malicious Example:**
```C
123    86651.814832    02:aa:bb:cc:00:01    02:aa:bb:5f:9e:4e    ARP    42    192.168.10.1 is at 02:aa:bb:cc:00:01

257    202650.110137   02:fe:fe:fe:55:55    02:aa:bb:14:b6:8b    ARP    42    192.168.10.1 is at 02:fe:fe:fe:55:55
```

**Indicators:**

- **Two different MAC addresses** claiming the same IP address (`192.168.10.1`)
- First MAC: `02:aa:bb:cc:00:01` (potentially legitimate gateway)
- Second MAC: `02:fe:fe:fe:55:55` (attacker)
- Indicates impersonation of gateway IP

**Validation Steps:**

1. Verify legitimate gateway MAC address from network documentation
2. Compare both MACs against known infrastructure
3. Identify which MAC is forged

---

### 4. Detect Unsolicited ARP Replies

**Detection Method:**

- Filter for ARP replies without matching requests:
```C
arp.opcode == 2
```

- Analyze timeline to identify replies with no visible preceding requests
- Look for patterns:
  - Numerous replies with no visible requests
  - Repeated advertisement of same IP from suspicious MAC
  - Device keeps sending ARP replies claiming ownership when it shouldn't

**Forged ARP Pattern:**

Forged ARP poisoning typically uses unsolicited `is-at` replies (gratuitous/unasked replies). Legitimate replies typically correspond to recent `who-has` requests.

**Suspicious Pattern:**
- Reply arrives without request in capture
- Same IP advertised repeatedly from same MAC
- MAC address not matching known network devices

---

### 5. Narrow Down to Attacker MAC Address

**Detection Method:**

- Filter for ARP replies from suspected attacker MAC claiming gateway or victim IP:
```C
arp.opcode == 2 && arp.src.proto_ipv4 == {GATEWAY_VICTIM_IP} && eth.src == 02:fe:fe:fe:55:55{ATTACKER}
```

**Example:**
```C
arp.opcode == 2 && arp.src.proto_ipv4 == 192.168.10.1 && eth.src == 02:fe:fe:fe:55:55{ATTACKER}
```

**Indicators:**

- All ARP replies for gateway IP originating from attacker MAC
- Frequency of replies (multiple per second indicates active poisoning)
- Timeline showing sustained attack pattern
- Victim devices likely poisoned if replies accepted

**Confirmation:**

Compare attacker MAC against:
- Known network infrastructure MAC addresses
- DHCP lease tables
- Switch MAC address tables
- Previous baseline captures

---

### 6. Analyze ARP Traffic Volume

**Detection Method:**

- Filter for all ARP requests to identify abnormal volume:
```C
arp.opcode == 1
```

- Analyze packet count per source MAC address
- Look for spikes in ARP traffic

**Indicators:**

- **Abnormal ARP Traffic Volume:** Large number of ARP packets in short intervals
- Normal: Periodic requests for unknown IPs (every few minutes)
- Malicious: Hundreds of ARP requests/replies in seconds
- **ARP Probe/Reply Loops:** Many requests with `Who has 192.168.1.x? Tell 192.168.1.y` patterns

**Validation:**

- Compare traffic volume to baseline
- Identify source of excessive ARP traffic
- Correlate with other suspicious indicators

---

### 7. Detect Gateway Redirection Patterns

**Detection Method:**

- Analyze ARP cache for multiple destination MACs for same gateway IP
- Filter ARP replies specifically for gateway:
```C
arp.opcode == 2 && arp.src.proto_ipv4 == {GATEWAY_IP}
```

**Indicators:**

- **Multiple destination MACs for same gateway IP**
	- Legitimate scenario: Redundancy/backup gateways (needs investigation)
	- Malicious scenario: Attacker MAC alternating with legitimate gateway MAC
- **Pattern analysis:** Frequency of MAC changes for gateway IP

**Note:** Gateway redundancy is legitimate but requires verification against network architecture documentation.

## Observables & Indicators
---

**Gratuitous ARP Indicators:**

- `arp.isgratuitous == True`
- Sender IP and Target IP are identical
- Target MAC is broadcast (`ff:ff:ff:ff:ff:ff`)
- No corresponding ARP request in capture
- High frequency (multiple per second)

**Duplicate MAC-to-IP Mapping Indicators:**

- Multiple MACs claiming same IP address
- Typically targeting gateway IP (`192.168.10.1`)
- One MAC matches known infrastructure, other is unknown
- Timeline shows alternating MAC addresses for same IP

**Unsolicited Reply Indicators:**

- ARP reply (`opcode == 2`) without preceding request
- Repeated replies for same IP-to-MAC mapping
- Replies from MAC not matching known devices
- Pattern of continuous unsolicited replies

**Traffic Volume Indicators:**

- Spike in ARP packet count (baseline: periodic, malicious: hundreds/second)
- Single MAC generating excessive ARP traffic
- ARP probe/reply loops with similar IP patterns

**Gateway Redirection Indicators:**

- Gateway IP associated with multiple MAC addresses
- Unknown MAC claiming gateway IP
- Legitimate gateway MAC replaced by attacker MAC in victim caches

## Tuning Notes
---

**Known False Positives:**

- **Gratuitous ARP:** Legitimate during network changes, DHCP renewals, failover events
- **Duplicate MACs:** Load balancers and redundant gateway configurations
- **High ARP volume:** Network scans, inventory tools, large subnet enumeration

**Allowlists:**

- Known infrastructure MAC addresses (gateways, routers, switches)
- Legitimate network management tools performing ARP scans
- DHCP servers sending gratuitous ARP during lease assignments

**Tuning Recommendations:**

- Baseline ARP traffic during normal operations
- Document legitimate infrastructure MAC addresses
- Set thresholds for ARP traffic volume based on network size
- Correlate ARP anomalies with other MITM indicators (DNS spoofing, SSL stripping)
- Monitor specific high-value targets (admin workstations, servers)

**Data Quality Considerations:**

- Packet captures must include full ARP traffic (not sampled)
- Time synchronization critical for timeline analysis
- Network tap or SPAN port required for comprehensive capture
- Switch port security and ARP inspection may prevent visibility

**SOC Caveats:**

- ARP attacks are Layer 2 and localized to broadcast domain
- Detection requires network-level visibility (not just endpoint logs)
- Remediation requires network-level response (not just endpoint isolation)
- Coordinate with network team for MAC address verification
